## 1. Scope — endpoint selection

One end-to-end workflow, reused across all three scenarios, covering all three groups:

```
login (auth)  →  search products + product detail (read)  →  add-to-cart + apply-coupon + checkout (transactional)
```

| Group | FR | API | Justification |
|---|---|---|---|
| Auth-heavy | FR20 | `POST /api/login` | JWT issuance; account-lockout rule (3 fails / 30s) on wrong password |
| Read-heavy | FR05/FR15 | `GET /api/products?search=`, `GET /api/products/:id` | read-dominant, cache/DB-read bound |
| Transactional | FR07/08/09 | `POST /api/cart`, `POST /api/apply-coupon`, `POST /api/checkout` | writes + coupon calc; latency-sensitive path |

Selection matches my HW02 features (FR04/FR09/FR15/FR20) and is not duplicated with group members.

## 2. Test design (AI-assisted, step-by-step)

The plans were generated by driving the AI step by step (endpoint mapping → CSV design → base
`.jmx` → scenario variants), **not** with a single generic prompt. Full prompt/response log in the
AI Audit Report appendix. Generator: `test-plans/generate_plans.js` (parameterized, reproducible).

**Data-driven inputs (CSV):**
- `data/users.csv` — 50-user pool (pre-registered via `POST /api/register`).
- `data/products.csv` — 5 SKUs (id, name, price, search term).
- `data/coupons.csv` — SAVE10 / BIGBUY / VIP100 with thresholds.

**Scenario parameters** (threads/ramp/duration exposed via `${__P(...)}`):

| Scenario | Threads (VU) | Ramp-up | Duration | Think-time | Listener (distinct) | File |
|---|---|---|---|---|---|---|
| Load | 50 | 60 s | 10 min | 1–2 s | **Summary Report** | `23127249_Load_20260830.jmx` |
| Stress | ramp→300 | 180 s | 6 min | 0.3–0.7 s | **Aggregate Report** | `23127249_Stress_20260830.jmx` |
| Spike | 200 burst | 3 s | 90 s | 0.1–0.3 s | **View Results Tree** | `23127249_Spike_20260830.jmx` |

Three distinct report views (Summary / Aggregate / View Results Tree) — no type repeated. HTML
dashboards additionally generated via `-e -o` for every run.

**Parameter justification:** think-time models real user pauses so throughput isn't unrealistically
inflated; Load ramp (60 s) avoids a cold-start thundering herd; Stress ramps gradually to 300 to
locate the knee; Spike uses a near-instant 3 s ramp to test burst recovery.

## 3. Human review — what the AI got wrong / missed

Critical review of the first AI-generated plan and the corrections I made (I am responsible for the
final plans):

| # | AI mistake / omission | Correction | Why the AI missed it |
|---|---|---|---|
| 1 | Guessed coupon endpoint as `/api/coupons/apply` | Real path is `POST /api/apply-coupon` | Model inferred from REST convention instead of reading the SUT's `api_specification.md` |
| 2 | Extracted only the JWT `token` from login | Also extract `user.id` → needed by `apply-coupon` body | Prompt didn't state the coupon body needs `user_id`; model didn't cross-read the two specs |
| 3 | Reused a single seed account for all VUs | Pre-registered a 50-user pool via CSV | Only 2 users are seeded; a single user gives unrealistic cache locality and risks lockout |
| 4 | No `Authorization` header on cart/coupon/checkout | Added a Bearer HeaderManager scoped to the transactional samplers | Model treated all samplers uniformly; missed that only these require auth |
| 5 | Averages-only reporting suggestion | Report p95/p99 for tail latency | LLMs default to "average latency" framing; averages hide the tail |
| 6 | Optimistic think-time (near-zero) for Load | Set realistic 1–2 s think-time for Load | Model optimizes for high throughput numbers, not realism |
| 7 | (Tooling) piping JMeter stdout through `head` | Capture full output, filter after | SIGPIPE killed the run early — an environment issue, not a plan flaw |

Account-lockout handling: the workflow logs in with valid pooled credentials, so the 3-fail/30 s
lockout does **not** trigger during Load/Stress/Spike. Reset procedure documented in the runbook
for the case of deliberate wrong-password testing.

### 4.2 Stress (`23127249_Stress_20260830` — Aggregate Report)
Ramp 0→300 VU over 180 s, 6 min. **0 errors / 32 215 samples**, throughput 90 req/s. Latency
barely rose: overall p95 9 ms, worst single sample 67 ms (checkout). The backend did **not**
reach a breaking point — no knee in latency, no errors — so 300 VU is within capacity on this
hardware. Checkout p95 12 ms, login p95 9 ms.

### 4.3 Spike (`23127249_Spike_20260830` — View Results Tree)
200 VU injected in 3 s, held 90 s. **0 errors / 17 453 samples**, peak throughput 196 req/s
(highest of all scenarios). The instantaneous burst pushed p95 to 13 ms and login p95 to 13 ms
(the auth path feels the burst most), but the system absorbed and recovered with zero failures.

### 4.4 Endurance / soak threshold
Load plan at 40 VU sustained for **11.9 minutes** (`-JDURATION=720`). Result over the full window:
**0 % errors, throughput 5.25 req/s, p95 7 ms, p99 10 ms** — no latency drift, no error creep.
Backend `node.exe` resource timeline (`evidence/resource_timeline.png`, sampled every 2 s):

- **Memory ceiling:** ~72 MB working set (started ~45 MB, stabilised 65–72 MB — **no leak** over 12 min).
- **CPU:** negligible (<1–2 %); the backend is not CPU-bound.
- **Peak threads:** 32.

**Threshold conclusion (with numbers):** on `ThieuNagg` (i5-12500H, 16 GB) the EShop backend
sustained **~90 req/s at 300 VU** and a **~196 req/s burst** with **0 % errors and p95 ≤ 16 ms**,
memory capped at **~72 MB**. The empirical limit reached in these tests was the **JMeter client +
think-time**, not the server — the SUT (single-node SQLite, 5-product dataset, sub-ms queries) has
headroom beyond what one JMeter instance on the same machine could generate. To truly saturate it
would require a distributed JMeter setup or a much larger dataset; documented as a limitation.
